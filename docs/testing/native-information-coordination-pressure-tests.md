# Native information coordination pressure tests

This file records concise RED/GREEN behavior evidence for Elephant skills. It stores no connector
payloads, opaque external IDs, or certification transcript.

## setup-workspace — RED baseline

Scenario: initialize a configured Linear/Notion single-Product repository in twenty minutes, with
an explicit instruction not to build providers, databases, authentication, transactions, or repeat
owner review.

Observed current-skill behavior:

- stopped without initializing because the Notion SetupAdapter was not certified;
- proposed three Notion databases and Product/Kind/status administration;
- required a complete manifest fingerprint and later fingerprint approval;
- planned stable keys, typed ID slots, byte hashes, execution IDs, manual-resume bearer,
  disposable certification records/relationships, cleanup proof, atomic container switching,
  receipts, identity attestation, and retained recovery evidence;
- produced no useful Linear, Notion, or local result for the configured small repository.

RED verdict: failed. The skill protected an internal provider protocol instead of completing the
owner's minimal information setup.

## setup-workspace — GREEN

The rewritten skill and its three native-information references were tested against the same
scenario plus multi-Product, wrong Linear browser tenant, interrupted create, and single-to-multi
transition variants.

Observed behavior:

- discovered repository, Linear, Notion, and Git context without writes and kept Products separate
  from engineering domains;
- proposed only current entry points and one final config projection, followed by one approval;
- used native scoped search, create/reuse, and semantic read-back, with browser setup limited to an
  already approved Linear administrative gap after tenant proof;
- kept a label-free single Product and deferred empty planning or knowledge structure;
- preserved the old config through interrupted or incomplete single-to-multi classification;
- stopped safely on wrong tenant, ambiguous native objects, uncertain results, or changed semantic
  preconditions without repeating the approved product decision;
- reconciled uncertain ordinary creates, Notion page creates, and append-only Linear Issue comments
  by exact native scope, with zero/one/multiple handling and one retry only after connector health
  plus two fresh authoritative reads across the normal consistency window;
- wrote config only after all required external results were verified and retained only a
  short-lived operation branch and human-readable pending note during application.

GREEN verdict: passed all five scenarios. The normal configured single-Product path is small enough
for the twenty-minute target and introduces no custom integration infrastructure or extra owner
gate.

## shape-story — RED baseline

Scenario: start from a one-sentence Product idea with an existing Linear Story/planning context and
one directly linked Notion Decision.

The current skill preserved its strong product-only discussion and one recap approval, but failed
the coordination behavior:

- it read repository roadmap/spec files instead of starting from the Linear Story and following its
  direct Notion relation, so it could repeat already settled product questions;
- it did not assess dependencies, conflicts, priority impact, or roadmap consequences;
- it had no `linear_only`, `decision`, `knowledge`, or `decision_and_knowledge` disposition;
- recap approval updated only a repository Product Contract and performed no native Linear/Notion
  write or read-back;
- it created and retained a Git Product Contract from the beginning of shaping.

RED verdict: failed. The user-facing conversation was sound, but its inputs and outputs still made
Git Product Contract files the center of product coordination.
